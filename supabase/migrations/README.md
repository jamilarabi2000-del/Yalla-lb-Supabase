# Migrations

## Read this before trusting a file in here

**69 of the files dated on or before `20260916` are two-line stubs.** They read:

```
-- Compatibility marker: migration already applied to the linked Supabase project.
```

They contain no DDL. The schema they claim to describe exists only in the hosted
project. Applying this directory to an empty database will **not** reproduce
production — it will produce almost nothing.

This is not a cosmetic problem. It is what allowed
`20260917010000_fix_product_atomic_optional_fields.sql` to be written, reviewed
and committed while the deployed function kept rejecting every product create,
for as long as nobody compared the two.

Everything dated `20260917022835` or later is a real migration containing the
DDL it describes.

## Rules

1. A migration is not done when the file is committed. It is done when it has
   been **applied to the project and the fingerprint has been refreshed**.
2. After applying migrations, run `npm run db:fingerprint -- --write` and commit
   `supabase/schema-fingerprint.json` in the same change.
3. CI runs `npm run db:verify`, which fails when the live schema and this
   repository disagree.

## Producing a real baseline

The stubs should eventually be replaced by one authoritative baseline. That must
be generated by a tool reading the database directly — never transcribed by
hand, which reintroduces exactly the drift this file warns about:

```bash
supabase link --project-ref yjmpjuskgbbshrvhgmys
supabase db pull --schema public,private,storage
```

Commit the generated file as `00000000000000_baseline.sql`, then move the stubs
into `supabase/migrations/_archive/` so the replay order is unambiguous. Eleven
stub basenames are currently duplicated under two different timestamps, so
replay order is ambiguous until that is done.
